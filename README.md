# WhiteList CRM API

Решение **задания Б — Software Developer** для WhiteList & Co Ltd: организации, результаты звонков и назначение встреч.

**TypeScript · Node.js · SQLite · 37 автотестов · без внешних зависимостей.**

Главные свойства: проверка рабочих часов в `Asia/Almaty`, защита бронирований внутри транзакции и на уровне БД, неизменяемое исходное время встречи и история переносов. Авторизация, роли, интерфейс, очереди, уведомления и кэш намеренно не добавлены по условиям задания.

## Запуск с нуля

Нужен **Node.js 24.12+**; рекомендуемая ветка — Node.js 24 LTS. `npm` поставляется вместе с Node.js. Для установки Node через уже установленный nvm можно выполнить `nvm install && nvm use` в папке проекта.

Распакуйте архив и перейдите в папку `whitelist-crm` либо клонируйте репозиторий. Из корня проекта выполните одну команду:

```sh
npm start
```

API: `http://127.0.0.1:3000`. Установка пакетов, сборка TypeScript, копирование `.env` и ручное создание БД **не нужны**. При первом старте создаётся `data/crm.sqlite`, выполняются SQL-миграции и добавляются два демонстрационных менеджера с ID `1` и `2`. Повторный старт сохраняет данные; миграции учитываются в `schema_migrations`.

Проверка запуска в другом терминале:

```sh
curl -i http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/managers
```

Остановка — `Ctrl+C`. Приложение закрывает HTTP-сервер и соединение с БД.

### Docker, альтернативный запуск

Нужны Docker Engine и Compose v2:

```sh
docker compose up --build
```

Адрес тот же; данные сохраняются в именованном томе `crm-data`, контейнер работает под пользователем `node`. Остановка: `docker compose down`. Команда `docker compose down -v` удаляет данные, поэтому для обычной остановки её использовать не нужно.

### Переменные окружения

Все переменные необязательны:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | Интерфейс HTTP-сервера; в контейнере `0.0.0.0` |
| `PORT` | `3000` | Порт от 1 до 65535; `0` выбирает свободный порт автоматически |
| `DATABASE_PATH` | `./data/crm.sqlite` | Путь относительно текущей папки или абсолютный путь |

Пример для macOS/Linux:

```sh
PORT=3001 DATABASE_PATH=./data/demo.sqlite npm start
```

Для `.env` предусмотрен шаблон; загрузка файла явная:

```sh
cp .env.example .env
node --env-file=.env src/server.ts
```

## Проверка

```sh
npm test
```

37 тестов используют настоящий SQLite, SQL-миграции и HTTP-парсер Node.js. Для HTTP-тестов байты запроса передаются через поток в памяти: это позволяет проверять JSON, коды ответов и заголовки без открытия сетевого порта. Конкурентные тесты запускают отдельные worker threads, у каждого своё соединение с одним файлом SQLite; это не последовательные вызовы одного сервиса. Проверены также восемь одновременных бронирований, гонка отмены и регистрации звонка, 10 080 минут недельного календаря и все 21 примера из `examples/requests.http`.

Дополнительная проверка на машине, где разрешены локальные порты:

```sh
npm run test:network
```

Она запускает настоящий `src/server.ts` дочерним процессом на порту, выбранном ОС, обращается к нему по TCP, проверяет сохранение данных после перезапуска и `SIGTERM`. GitHub Actions настроен на обе команды для Node.js 24 и 26 и отдельный запуск Docker Compose; удалённый CI в рамках этой сборки не запускался.

**Фактически проверено:** `npm test` — 37/37 на Node.js 26.13.0, включая проверку после чистой распаковки итогового архива; синтаксис точки входа и сетевого теста; `docker compose config --quiet`. **Ограничения среды:** попытка сетевого теста завершается `listen EPERM`, а доступ к Docker daemon запрещён, поэтому реальный TCP и контейнерный запуск здесь не подтверждены. Нативный запуск TypeScript удаляет аннотации, но не выполняет статическую проверку `tsc`; отдельный компилятор в проект не включён. ## HTTP API

Все тела запросов — `application/json`, ID — положительные целые числа, дата/время в ответах — UTC. Неизвестные поля, параметры и повторяющиеся query-параметры отклоняются. Максимальное тело запроса — 16 KiB.

| Метод и путь | Вход / назначение | Успех |
| --- | --- | --- |
| `POST /companies` | `name`, `bin`, `phone` | `201` |
| `GET /companies` | `status`, `page=1`, `pageSize=20` (макс. 100) | `200` |
| `POST /calls` | `companyId`, `result`, опционально `meetingId`, `notes` | `201` |
| `POST /meetings` | `companyId`, `managerId`, `startsAt` | `201` |
| `PATCH /meetings/{id}` | Только `startsAt` либо только `status: "cancelled"` | `200` |
| `GET /managers/{id}/schedule?date=YYYY-MM-DD` | Расписание за календарный день в Almaty | `200` |
| `GET /companies/{id}` | Организация и статус последнего звонка | `200` |
| `GET /meetings/{id}` | Встреча с полной историей | `200` |
| `GET /managers` | ID демонстрационных менеджеров | `200` |
| `GET /health` | Проверка API и соединения с БД | `200` |

`GET /companies` возвращает `{ data: [...], pagination: { page, pageSize, total, totalPages } }`. Порядок фиксирован по ID. Пустая страница возвращает `200`, пустой массив и корректный `total`; счётчик и страница читаются в одной транзакции.

### Пример последовательности

Для новой пустой базы первый ID компании и встречи равен `1`. Если база уже содержит записи, используйте ID из ответа.

```sh
curl -i -X POST http://127.0.0.1:3000/companies \
  -H 'Content-Type: application/json' \
  -d '{"name":"ТОО Demo","bin":"000000000101","phone":"+77010000001"}'

curl -i -X POST http://127.0.0.1:3000/meetings \
  -H 'Content-Type: application/json' \
  -d '{"companyId":1,"managerId":1,"startsAt":"2026-11-23T05:00:00Z"}'

curl -i -X POST http://127.0.0.1:3000/calls \
  -H 'Content-Type: application/json' \
  -d '{"companyId":1,"result":"meeting_set","meetingId":1,"notes":"Клиент подтвердил встречу"}'

curl -i 'http://127.0.0.1:3000/managers/1/schedule?date=2026-11-23'

curl -i -X PATCH http://127.0.0.1:3000/meetings/1 \
  -H 'Content-Type: application/json' \
  -d '{"startsAt":"2026-11-24T06:00:00Z"}'

curl -i http://127.0.0.1:3000/meetings/1
```

Полный файл запросов с отменой и ошибочными сценариями: [examples/requests.http](examples/requests.http). Данные организаций в примерах синтетические.

### Ошибки

```json
{
  "error": {
    "code": "MANAGER_OVERLAP",
    "message": "Manager already has a meeting during this time.",
    "requestId": "UUID запроса"
  }
}
```

| HTTP | Когда |
| --- | --- |
| `400` | Синтаксически неверный JSON или URL |
| `404` | Не найден менеджер, организация, встреча или маршрут |
| `405` | Метод не разрешён для маршрута; заголовок `Allow` |
| `409` | Пересечение, активная встреча организации, повторный БИН, перенос отменённой встречи |
| `413` | Тело больше 16 KiB |
| `415` | Не `application/json` |
| `422` | Ошибка полей, даты, рабочих часов или связи `meeting_set` |
| `503` | SQLite остаётся занятой после таймаута; заголовок `Retry-After: 1` |
| `500` | Только неожиданный внутренний сбой; подробности не уходят клиенту |

## Принятые решения по неоднозначностям

1. **Активная встреча** — любая запись со статусом `scheduled`. У организации допускается только одна такая запись вообще, даже на другую дату или у другого менеджера. Это более строгое прочтение «двух активных встреч одновременно»; переносится существующая запись. Само наступление времени статус не меняет; завершение встреч не входит в API задания.
2. **Статус организации** — результат последнего зарегистрированного звонка: `no_answer`, `refused`, `meeting_set`; до звонков — `new`. Создание/отмена встречи не переписывают факт звонка: после отмены `meeting_set` может остаться статусом последнего контакта. Актуальные встречи видны в расписании.
3. **Звонок `meeting_set`** регистрируется после `POST /meetings` и явно ссылается на её `meetingId`. При записи проверяются существование, та же организация и статус `scheduled`; позднейшая отмена не уничтожает исторический звонок. Два запроса не являются одной общей транзакцией; встреча может существовать до регистрации звонка.
4. **Рабочий календарь** — пн–пт, 09:00–18:00 по IANA-зоне `Asia/Almaty`, без календаря праздников. Длительность ровно 3 600 000 ms. Проверяются секунды и миллисекунды: 17:00:00 допустимо, 17:00:00.001 — нет. Интервалы полуоткрытые `[начало, конец)`, поэтому соседние встречи разрешены.
5. **Время на входе** — UTC с `Z` или `+00:00`, обязательными секундами и до трёх знаков миллисекунд. Локальные значения и другие смещения отклоняются; ответы всегда в каноническом UTC с `Z`. `date` в расписании — локальный календарный день, а не timestamp. Прошедшие даты разрешены, поскольку запрета в ТЗ нет.
6. **Перенос** меняет только время, не менеджера или организацию. Пустой PATCH и одновременно перенос+отмена отклоняются. Повторная отмена и перенос на то же мгновение идемпотентны. Отменённая встреча не восстанавливается; создаётся новая.
7. **БИН** — уникальная строка из 12 цифр, включая ведущие нули. Проверка контрольной суммы и реестра юрлиц не предусмотрена. Телефон — E.164, название непустое до 200 символов, заметка непустая до 2000 символов; нулевые символы в текстовых полях отклоняются.
8. **Менеджеры** — две тестовые записи в SQL-миграции. CRUD менеджеров и пользователи не требуются; ID можно получить через `GET /managers`.

## Структура и защита от гонок

| Путь | Ответственность |
| --- | --- |
| `src/server.ts` | Конфигурация, запуск, завершение |
| `src/http/` | HTTP, маршруты, единый формат ошибок |
| `src/domain/` | Валидация и правила организаций, звонков, встреч, времени |
| `src/db/database.ts` | Соединение, версионированные SQL-миграции, транзакции |
| `src/db/migrations/` | Таблицы, индексы, ограничения, аудит |
| `tests/` | Бизнес-правила, HTTP, файловая БД и конкуренция |
| `examples/` | Готовые HTTP-запросы |
| `docs/` | Объяснение решения для разбора на собеседовании |

Бронирование и перенос выполняются в `BEGIN IMMEDIATE`: блокировка записи берётся **до** проверки свободного времени. Все операции проверки/записи синхронные, без `await` внутри транзакции. Второй writer ждёт до 5 секунд, после освобождения блокировки повторно читает актуальные данные и получает `409`, если слот занят. Частичный UNIQUE-индекс ограничивает активную встречу организации; SQL-триггеры запрещают пересечения менеджера даже при обходе сервисного кода. История создаётся триггерами в той же транзакции, поэтому откат не оставляет ложных событий.

Рабочие часы проверяются в доменном коде через `Intl.DateTimeFormat`, а не фиксированный UTC-offset. База хранит целое число миллисекунд Unix; только граница HTTP преобразует значения в читаемые UTC-строки.

### Что сделано и что осталось

Все шесть обязательных эндпоинтов и семь бизнес-правил реализованы; есть миграция, демонстрационные менеджеры, автотесты, файл запросов, история Git и [REFLECTION.md](REFLECTION.md). Запуск приложения не обращается к npm registry. Использованы встроенные модули Node, чтобы небольшое задание оставалось воспроизводимым в среде без установки пакетов; это осознанный отказ от привычного веб-фреймворка.

Для реальной нагрузки следующие шаги: измерить ожидание блокировок, перенести хранение на PostgreSQL при необходимости, добавить optimistic locking для одновременного редактирования одной встречи и идемпотентность создания при повторе запроса после потери ответа. Сейчас последовательные изменения одной встречи используют последнее успешно записанное значение; история сохраняет оба изменения. SQLite здесь предполагает один хост с локальным диском: общий файл на сетевом диске и горизонтальный кластер не поддерживаются. Синхронный доступ к SQLite может блокировать event loop под нагрузкой. Статическая проверка типов и полный запуск Docker остаются отдельными пунктами валидации; успешные функциональные тесты их не заменяют.

Код и документация подготовлены с использованием ИИ, что разрешено ТЗ; детали в REFLECTION. Перед сдачей полезно пройти [docs/WALKTHROUGH.md](docs/WALKTHROUGH.md) и выполнить сетевой запуск на своей машине.
